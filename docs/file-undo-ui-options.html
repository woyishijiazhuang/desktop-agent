文件撤销 UI · 调研与候选方案

目标：为 write_file / edit_file 的撤销能力换一套更清晰的 UI。下面是市面主流做法的调研结论，以及 4 个可直接落地的候选方案（含可点击的交互 mockup）。请挑选或组合。

一、市面做法调研

产品 模型粒度 入口与交互 可借鉴点
Claude Code
/rewind 文档 		每个用户 prompt 一个 checkpoint（保留最近 100 个） /rewind 或输入框为空时连按两次 Esc → 弹出「checkpoint 列表」，选中某条后再选动作：还原代码/还原对话/两者/摘要/取消 动作是二次选择而非一堆按钮挤在列表里；代码与对话解耦（「只还原代码，保留对话」）；明确写了不可覆盖 bash 改动
Cursor
Agent 文档 		每轮对话一个 checkpoint hover 上一条用户消息 → 右下角出现 Restore Checkpoint → 一次性回滚该点之后所有文件改动（不动对话） 入口藏在「用户消息 hover」，不占聊天区；按时间点回退比按文件回退更符合直觉；官方明确此处是高频回归点（按钮丢失会引发大量投诉）→ 可见性要够
Cline
Checkpoints 文档 		每次 tool use 一个 checkpoint（影子 git） 对话流里插一条「Checkpoint」虚线 + 两个按钮：Compare（打开 diff）/ Restore（三选一：只还原文件 / 只还原任务 / 两者） 「Compare 先看再决定」的两段式心智；任务级「查看本次新增改动」汇总视图（View New Changes）解决了「文件多、逐个卡片点太慢」
Windsurf / Cascade
Cascade 文档 		每个 prompt 一个 step hover 原始 prompt 右侧的回退箭头，或从对话「目录（TOC）」里直接回退；不可逆，官方加粗提示谨慎 提供「目录/时间线」这种全局跳转入口，长会话里不用翻聊天记录；并且明示「不可逆」的风险提示文案
GitHub Copilot（VS Code / VS）
Agent Mode 文档 		每轮编辑 + 「上次保留/撤销之后」的累积差异 聊天区 Total changes 汇总 + 多文件 summary diff 单页查看，支持逐文件粒度 accept / undo；文档明确「不支持逐步 undo」 一个汇总 diff 页承载多文件审阅与选择性撤销，是「卡片内联」的天花板替代品

三条可迁移结论

  • 主流已从「文件级按钮」转向「时间点回退」：Cursor / Claude Code / Windsurf / Cline 都是一次性回退到某个时间点，而不是让用户逐个文件点撤销。原因是 agent 一轮会改多个文件，「逐文件」的心智负担高。
  • 回退动作普遍是「选点 → 选动作」两段式，且在菜单里用文字写清「会还原什么、不会还原什么」；对不可逆操作会显式警示。
  • 差异总览是刚需：Cline 的 Compare、Copilot 的 Total changes、Cursor 的 diff view 都在解决「我到底改了什么」。我们目前只能靠单个卡片里的 Monaco DiffEditor 逐个看。

交互

  • undoable 且「该文件没有更晚的改动」→ 显示可点按钮（保留两段式确认）
  • 有更晚改动 → 按钮置灰 + tooltip「请先撤销更晚的改动」（不再点了才报错）
  • 终态 → 「已撤销 / 已作废」标签（hover 显示原因）
  • 卡片展开后仍用现有 Monaco DiffEditor 看 diff

优点

  • 纯前端改动，零后端成本；今天就能修掉「点了才被拒」的体验坑
  • 保持「改动就地可撤」的空间连续性

缺点

  • LIFO 顺序仍要求用户自己理解「必须倒着撤」，跨文件时尤其反直觉
  • 文件多/卡片多时，找目标靠翻聊天记录，无全局视图
  • 与市面主流（时间点回退）方向不一致

后端工作量 几乎为零

  • 仅需在 FileChangeItem 增加一个「是否有更晚改动」的布尔位，或在渲染侧按 path 自己算（store 里已有全量数据，可直接算）

交互

  • hover 用户消息 → 右侧浮出 ⟲ 按钮（不占空间）

优点

  • 与 Claude Code / Cursor / Windsurf 一致，用户已有肌肉记忆
  • 「这一轮搞砸了」是最高频场景，一次点击解决，不用理解 LIFO
  • 复用现有卡片 diff，无需新视图

缺点

  • hover 入口可发现性差（Cursor 因此吃了大量投诉），建议同时在消息上常驻一个弱化图标
  • 必须实现 revertTo，且跨文件部分失败时要明确报告哪些没退成功
  • 不可逆（无 redo），误点代价大 → 需要二次确认

交互

  • 会话头部常驻「改动 N」徽标 → 打开右侧面板（或从侧栏会话菜单进入）
  • 按文件分组，组内按时间倒序列出每次改动，可展开 diff 预览
  • 支持勾选任意条 / 整文件 / 一键「全部撤销」（复用现有 undoSession）
  • 不可撤销的文件（二进制/超限/外部修改）就地显示原因，不静默消失

优点

  • 解决「文件多、卡片难找」的根本问题，长会话可用
  • 是 B 方案的前置基础设施：面板天然承载「回退到某点」的高级入口
  • 「改了什么」一览无余，误改能被发现（现状缺乏全局视图）
  • 勾选多条撤销可放宽 LIFO 限制：用户选中的集合内部按逆序自动串行执行

缺点

  • 多一个需要维护的面板（新组件 + 空态/加载态/分组逻辑）
  • 与卡片内联按钮存在一定功能重叠，需要想清楚两者分工

后端工作量 小

  • 列表数据已具备（listSessionChanges 含 path/时间/状态）
  • 勾选批量撤销：可前端串行调 undo(logId)（当次操作内按 id 倒序），或新增 undoMany(ids) 一次加锁执行、合并报告 failures

交互

  • 撤销成功后底部弹出提示条：告知「撤了什么」+ 提供「重做」，几秒后自动消失
  • 时间线：以用户 prompt 为节点，一眼看出每个阶段改了几个文件、能否回退

优点

  • 提示条把「刚发生什么、能不能反悔」讲清楚，降低误操作焦虑（Gmail 式心智）
  • 时间线可视化 agent 的工作节奏，长任务里更好定位「哪一轮开始跑偏」

缺点

  • 「重做」需要 redo（快照 + 状态机倒放），后端工作量最大
  • 提示条只对「最近一次」友好，与批量/多文件场景不一致
  • 时间线需要按用户消息聚合改动，后端要补 turnId 或时间区间归属
  • 视觉噪音偏高，可能干扰阅读

后端工作量 大

  • 新增 redo（或至少「撤销后可恢复」）；改动记录需带上所属用户消息

我的建议（供你否决）

  • 已落地：方案 B。后端 revertTo（阶段四）与消息级「回退到这里」入口已实现，见 docs/file-undo-design.md。注意当前实现用的是确认框而非 mockup 里的悬浮菜单，且不含「还原对话」（对话还原仍未支持）。
  • 仍待定：A + C。A 用极小成本修掉「点了才报错」（非最新改动时按钮置灰 + tooltip），C 提供全局改动视图与批量撤销；两者都只依赖现有后端能力。
  • D 暂不做。redo 会显著抬高状态机复杂度，而「撤销提示条」的价值可以用 C 面板的状态翻转 + toast 文案部分替代。
